C 言語（C++でもほぼ同様）では、ソースファイルをコンパイルして実行するまでにはいろいろな工程を通ります。この記事では、簡単なサンプルのコンパイルから始めて、これらの工程を説明しつつ、ソースファイルがどうコンパイルされて実行されるかを練習を交えながら学びます。動的リンクやクロスコンパイルのしくみを体感して理解できることがゴールです。

なお、C 言語についての基礎的な知識はあるものとします。練習のための環境は Linux を想定しています。この記事の実行例は WSL2 上の Ubuntu 22.04 で実行しており、環境によってはコマンドや出力が異なる可能性もありますのでご注意ください。

```text

```

## 機械語のイメージ

これからの話には、なんとなくでも機械語のイメージがあるほうがよいので、最低限のイメージがつかめる程度に説明します。まずは用語から。

- **レジスタ**: CPU 内部で演算の対象や結果などを一時的に覚えておくところ。
- **メモリ**: プログラムの命令やデータを記憶しておくところ。
- **アドレス**: メモリ上の各バイトの位置を示す番地。
- **命令**: CPU が実行する 1 ステップの処理（レジスタへの代入、加算、条件分岐、関数呼び出しなど）。
- **ラベル**: 人間やツールが特定のアドレスを参照しやすいように付けた名前。実際の機械語には含まれません。

機械語プログラムはこんな感じのものだと思ってください。

```
アドレス ラベル 命令
0000     main レジスタAに1を入れる
0001          subを呼ぶ → 0003を呼ぶ
0002          呼び出し元に戻る
0003     sub  レジスタAに1を足す
0004          レジスタAの内容をアドレスdatに保存する → レジスタAをアドレス0010に保存する
0005          呼び出し元に戻る
...
0010     dat
...
```

これからの話で大事なのは、`sub` や `dat` などが実際の機械語では `0003` や `0010` などといったメモリのアドレスになるというところです[^relative-address]。逆に言うと、`sub` や `dat` のアドレスがわかるまではプログラムが完成しません。ここ伏線なので頭の片隅に置いておいてください。

[^relative-address]: 実際の具体的な値はメモリアドレスそのものではないのですが、ここでは踏み込みません。後ほど説明します。

## コンパイルとリンク

C 言語で書いたソースコード（`.c`）を実行ファイルに変換することを「コンパイルする」と言いますが、このときコンパイラは実際には（狭い意味での）コンパイルとリンクというふたつの工程を行っています[^actually-more]。

[^actually-more]: ここでいう「コンパイル」もプリプロセス・（さらに狭い意味での）コンパイル・アセンブルといった工程に分かれています。

コンパイルは、人間が読むためのソースコードを、CPU が理解できる機械語に翻訳し、オブジェクトファイル（`.o`）を出力することです。オブジェクトファイルでは、プログラムの命令部分は機械語になっていますが、他のオブジェクトファイルやライブラリに含まれる関数や変数のメモリアドレスが不明なのでまだ実行できません。

リンクとは、複数のオブジェクトファイルやライブラリを結合し、関数などのメモリアドレスを解決して実行ファイルを出力することです。リンクを行うプログラムのことをリンカと言います。

### 実行ファイルを作成する

この練習では、ごく単純なソースファイルを作り、一気にコンパイル・リンクまで行って実行ファイルを作ります。

以下のファイルを作成します。`User` という構造体を作って値を設定し、表示するだけのものです。

```c:main.c
#include <stdio.h>
#include <string.h>

typedef struct {
    int id;
    char name[32];
} User;

void print_user(User *u) {
    printf("ID: %d, Name: %s\n", u->id, u->name);
}

int main() {
    User u;
    u.id = 100;
    strcpy(u.name, "Alice");
    
    print_user(&u);
    
    return 0;
}
```

実行ファイルを作成し、動かしてみます。`-o` オプションは実行ファイルの名前を指定するオプションです[^a-out]。

[^a-out]: 何も指定しないと `a.out` というファイル名ができます。

```text
$ ls
main.c
$ gcc main.c -o main
$ ls
main  main.c
$ ./main
ID: 100, Name: Alice
```

### いったんコンパイルしてからリンクする

次に、いったんコンパイルしてオブジェクトファイルを作り、それをリンクして実行ファイルを作成するやり方をやってみます。

オブジェクトファイルを作るには `-c` オプションを指定します。出力ファイル名を指定する必要はありません。

```text
$ rm main
$ ls
main.c
$ gcc -c main.c
$ ls
main.c  main.o
```

オブジェクトファイルをリンクして実行ファイルにするには、単にオブジェクトファイルを指定してやるだけで OK です。

```text
$ gcc main.o -o main
$ ls
main  main.c  main.o
$ ./main
ID: 100, Name: Alice
```

できました。

gcc のことを普段は単に「コンパイラ」と呼びますが、実は gcc 自体は全体の司令塔のような役割で、指定されたオプションやファイルの種類（`.c` か `.o` か、など）に応じて、内部で（狭い意味での）コンパイラやリンカを使い分けて呼び出しています。そのことを強調したいときは、gcc を「コンパイラドライバ」と呼びます。

`gcc -v main.c -o main` と `-v` をつけるとどのようなコマンドを実行しているかわかるのですが、わりといっぱい出力されるので関連する部分だけ抜き出しておきます。`cc1` がコンパイルを、`collect2` がリンクを行っています。

```text
$ gcc -v main.c -o main
...
 /usr/lib/gcc/x86_64-linux-gnu/11/cc1 ...
...
 /usr/lib/gcc/x86_64-linux-gnu/11/collect2 ...
...
```

リンクを行うと実行ファイル `main` ができますが、ファイルとしてディスク上にあるだけではプログラムは動きません。プログラムを実行するときは、OS がメモリ上にプログラムを読み込んで配置し、CPU に「ここから実行してね」と指示を出します。この処理を**ロード**（Load）、それを担当する OS のしくみを**ローダ**（Loader）と呼びます。ロード時に何が行われているかもおいおい説明していきます。

## シンボル

冒頭の「機械語のイメージ」で、機械語になると「ラベル」はメモリのアドレスに置き換わると説明しました。この「ラベル」のことをコンパイル・リンク・実行の文脈では「シンボル」、このシンボルはこのアドレスを指す、ということを覚えておく表を「シンボルテーブル」（Symbol table）と呼びます。

シンボルはこの記事の中でもっとも重要な概念なのでいろいろ調べながらイメージを固めていきます。

### オブジェクトファイル内のシンボルを調べる

オブジェクトファイルに含まれるシンボルを調べるツールを使って、`main.o` の中身を覗いてみます。

まずは、一番シンプルな `nm` というコマンドを使ってみます。もし手元の環境に入っていなかったら `binutils` パッケージをインストールしてください。Ubuntu であれば `sudo apt install binutils` ですね。

```text
$ nm main.o
                 U __stack_chk_fail
0000000000000037 T main
0000000000000000 T print_user
                 U printf
```

:::message
具体的な数字（`00...0037`）や自分で付けたものではない名前（`__stack_chk_fail`）などは、環境によって異なる可能性があります。適宜読み替える・無視するなどして進めてください。これ以降全体で同様です。
:::

真ん中にあるアルファベットは、シンボルの状態を表しています。

- `T` (Text): そのファイル内にコード（プログラムの実体）が存在することを示します。
- `U` (Undefined): そのファイル内には実体がない未定義のシンボルです。

`main` と `print_user` は `main.c` の中で書いたので、ここに実体があります。

`printf` は C 言語の標準ライブラリ（libc）にある関数なので、`main.o` の中には実体がありません。そのため「`printf` という関数を呼ぶ予定だけど、実体はここにはないよ」という状態になっています。`__stack_chk_fail` はコンパイラが自動で挿入した保護機能の関数ですが、この記事では詳細には踏み込みません。無視しておいて大丈夫です。

:::details なぜ strcpy は表示されないのか？
標準ライブラリからは `strcpy` も使ってるのに `printf` だけしかないのはなぜかというと、`"Alice"` という固定で短い文字列の `strcpy` なので、`strcpy` を呼び出すのではなく `main` の中に直接文字列をコピーする機械語が書き込まれている（インライン展開されている）からです。
:::

次に、`readelf` コマンドでもう少し詳しく調べてみます。

Linux のオブジェクトファイルや実行ファイルは、**ELF**（Executable and Linkable Format）という共通の形式で作られています。ELF にはリンクや実行のために必要な様々な情報が記録されています。これらの情報を読むためのツールが `readelf` です。

`-s` オプションでシンボルテーブルを表示してみます。

```text
$ readelf -s main.o

Symbol table '.symtab' contains 8 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND 
     1: 0000000000000000     0 FILE    LOCAL  DEFAULT  ABS main.c
     2: 0000000000000000     0 SECTION LOCAL  DEFAULT    1 .text
     3: 0000000000000000     0 SECTION LOCAL  DEFAULT    5 .rodata
     4: 0000000000000000    55 FUNC    GLOBAL DEFAULT    1 print_user
     5: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND printf
     6: 0000000000000037    93 FUNC    GLOBAL DEFAULT    1 main
     7: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND __stack_chk_fail
```

`Ndx` の列を見ると、`printf` と `__stack_chk_fail` が `UND`（未定義）になっていることがわかります。これは先ほどの `nm` の `U` と同じ意味です。`print_user` の行を例にとると、その他にも `Type` が `FUNC`（関数）であることや、`Size`（関数の機械語のサイズ）、`Value`（先頭からの位置）など、`nm` よりも詳細な情報が ELF に記録されていることがわかります。

また、`Type` が `SECTION` となっている `.text` や `.rodata` にも注目してください。ELF ファイルの中身はデータの種類ごとに「セクション」という区画に分けて管理されています。`.text` は機械語のプログラムコードが入る区画（`nm` の `T (Text)` もここから来ています）、`.rodata`（Read-Only Data）は `"ID: %d, Name: %s\n"` のような書き換えられない定数データが入る区画です。`.text` の `Ndx`（セクション番号）が `1` で、`print_user` や `main` の `Ndx` も `1` になっているのは、「これらの関数の実体は `.text` セクションに入っているよ」ということを表しています。

### 機械語の中身を覗いてみる

さらに、機械語そのものを人間が読めるアセンブリ言語に逆変換（逆アセンブル）して表示する `objdump -d` コマンドを使ってみましょう。

```text
$ objdump -d main.o
```

ずらっと機械語やアセンブリ言語が出力されるはずです。ここでは関数を呼び出している部分（`call` 命令）に注目してみます。

```text
Disassembly of section .text:

0000000000000000 <print_user>:
  ...
  2a:   b8 00 00 00 00          mov    $0x0,%eax
  2f:   e8 00 00 00 00          call   34 <print_user+0x34>
  34:   90                      nop
  ...

0000000000000037 <main>:
  ...
  71:   48 89 c7                mov    %rax,%rdi
  74:   e8 00 00 00 00          call   79 <main+0x42>
  79:   b8 00 00 00 00          mov    $0x0,%eax
  ...
```

左端の `2a:` や `71:` はアドレス（先頭を `0` とした位置）です。

アドレス `2f` は `print_user` から `printf` を呼び出している場所、アドレス `74` は `main` から `print_user` を呼び出している場所です。機械語の `e8` は関数呼び出し（call）命令ですが、その右に続く呼び出し先のアドレスが `00 00 00 00` とゼロで埋められています。コンパイルした直後のオブジェクトファイルでは、呼び出し先の関数がメモリのどこに置かれるかまだ決まっていないため、仮にゼロが入っているのです。このゼロ埋めの部分を、正しいアドレスに書き換えるのがリンカの役割のひとつです。

### リンク後のシンボルと機械語を調べる

では、リンク後の実行ファイル `main` で、先ほどのアドレスはどう変化したでしょうか？実際に見てみましょう。

```text
$ objdump -d main
```

出力の中から、`print_user` 関数と `main` 関数の部分を見てみます。

```text
0000000000001169 <print_user>:
    1169:	f3 0f 1e fa          	endbr64 
    116d:	55                   	push   %rbp
    ...
```

アドレス `1169` に `print_user` 関数が配置されています。

```text
00000000000011a0 <main>:
    ...
    11d6:	48 8d 45 d0          	lea    -0x30(%rbp),%rax
    11da:	48 89 c7             	mov    %rax,%rdi
    11dd:	e8 87 ff ff ff       	call   1169 <print_user>
    11e2:	b8 00 00 00 00       	mov    $0x0,%eax
    ...
```

`main` 関数の中（アドレス `11dd`）の `call` 命令を見てください。リンク前は `e8 00 00 00 00` とゼロで埋められていた部分が、`e8 87 ff ff ff` に書き換わっています。

`87 ff ff ff` とは何でしょうか？実はこれは 16 進数の `ffffff87` のことで、`-121` を意味しています[^int-representation]。`e8` (call 命令) と組み合わせると、現在のアドレスから 121 バイト分だけメモリを遡ったアドレス（1169）を呼ぶ、ということになります。そこに `print_user` があるというわけです。`objdump` の `call   1169 <print_user>` という表示はそれを表しています。

[^int-representation]: なぜ `ffffff87` なのか、`-121` なのかは「エンディアン」「2 の補数」を調べてみてください。

ここで、「機械語のイメージ」では `subを呼ぶ → 0003を呼ぶ` のように実際のアドレスを使っていたことを思い出した人もいるかもしれません。実際の機械語でも単に `1169` とアドレスを書けばいいのにと思うかもしれませんが、この方がいろいろ利点があってこうなってきました。ローダのお仕事にも関係してくるんですがこの記事では踏み込みません。

`1169` とアドレスそのものを書いたものを「絶対アドレス」、`ffffff87` のように現在のアドレスとの相対的な位置でアドレスを表すことを「相対アドレス」と言います。

### 外部ライブラリのシンボルを調べる

では、`main.c` 内では定義していない `printf` はどうなったでしょうか？`printf` は `stdio.h` で宣言されているものを読み込んでいますが、実体はどこからも参照していないように見えます。もちろん実体がないと実行できないはずですが、どうなっているのでしょうか。

リンク後のシンボルを `readelf -sW main` で見てみます。`W` は Wide に表示するためのオプションです。つけないと関数名が省略されてしまうのでつけました。

```text
$ readelf -sW main

Symbol table '.dynsym' contains 8 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     ...
     3: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND __stack_chk_fail@GLIBC_2.4 (3)
     4: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND printf@GLIBC_2.2.5 (4)
     5: 0000000000000000     0 NOTYPE  WEAK   DEFAULT  UND __gmon_start__
     ...

Symbol table '.symtab' contains 38 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
    ...
    31: 0000000000004010     0 NOTYPE  GLOBAL DEFAULT   26 __bss_start
    32: 00000000000011a0    93 FUNC    GLOBAL DEFAULT   16 main
    33: 0000000000001169    55 FUNC    GLOBAL DEFAULT   16 print_user
    34: 0000000000004010     0 OBJECT  GLOBAL HIDDEN    25 __TMC_END__
    ...
```

いろいろ知らないワードがあると思いますが知らないところはスルーで。

シンボルテーブルが `.dynsym`（動的シンボルテーブル）、`.symtab`（通常のシンボルテーブル）に分かれています。`main` や `print_user` は通常のシンボルテーブルに含まれ、具体的なアドレスが割り当てられています。`printf` は動的シンボルテーブルに含まれ、実行ファイルになった後も `UND`（未定義）のまま残っています。

動的シンボルテーブルに含まれるシンボルは、実行時にはじめてシンボルの値が決まります。`printf` は動的ライブラリ(.so)としてプログラム本体とは別に提供されており、プログラムが起動するとき（ロード時）に、ローダが動的ライブラリを探してきて、それを参照しながらアドレスを決めるしくみになっています。動的ライブラリについては、後の章で詳しく体験します。

## 複数オブジェクトファイルのリンク

プログラムが大きくなってくると、すべての処理を 1 つのファイルに書いていては大変ですし、関数や変数のスコープが広がって保守性も悪くなります。プログラムが大規模になるにしたがってソースコードは多くのファイルに分かれていくのが普通です。「リンクする」という言葉も、複数ファイルを結合するというところから来ています。

### 複数のオブジェクトファイルをリンクする

この章では、ユーザーを扱う処理（`user.c`）と、メインの処理（`main.c`）にファイルを分割してみましょう。

C 言語のコンパイラは、一度に 1 つのソースファイルしか読み込みません。`main.c` をコンパイルするとき、コンパイラは `print_user` という関数がどんな引数を取るのかを知らないとエラーを出してしまいます。そこで、「こういう名前で、こういう引数を取る関数があるよ」とコンパイラにあらかじめ知らせておく宣言（プロトタイプ宣言）をヘッダファイル（`.h`）に書いておきます。

さきほど作ったソースコードを以下の 3 つに分割します。

- `user.h`: `User` 構造体と `print_user` 関数のプロトタイプ宣言
- `user.c`: `print_user` 関数の実装
- `main.c`: `main` 関数（`user.h` をインクルードして `print_user` を呼び出す）

```c:user.h
typedef struct {
    int id;
    char name[32];
} User;

void print_user(User *u);
```

```c:user.c
#include <stdio.h>
#include "user.h"

void print_user(User *u) {
    printf("ID: %d, Name: %s\n", u->id, u->name);
}
```

```c:main.c
#include <string.h>
#include "user.h"

int main(void) {
    User u;
    u.id = 100;
    strcpy(u.name, "Alice");

    print_user(&u);

    return 0;
}
```

まずは、それぞれのファイルを個別にコンパイルしてオブジェクトファイル（`.o`）を作ります。

```text
$ rm main
$ gcc -c user.c
$ gcc -c main.c
$ ls
main.c  main.o  user.c  user.h  user.o
```

出来上がった 2 つのオブジェクトファイルのシンボルを `nm` で確認してみましょう。

```text
$ nm main.o
                 U __stack_chk_fail
0000000000000000 T main
                 U print_user

$ nm user.o
0000000000000000 T print_user
                 U printf
```

`main.o` では `print_user` が `U`（未定義）ですが、`user.o` では `T`（実装あり）になっています。

では、この 2 つのオブジェクトファイルをリンカに渡して結合してみます。

```text
$ gcc main.o user.o -o main
$ nm main
...
0000000000001169 T main
00000000000011c6 T print_user
                 U printf@GLIBC_2.2.5
...
$ ./main
ID: 100, Name: Alice
```

2 つのファイルがきちんと結合され、正しく実行できました。シンボルはというと、`main` と `print_user` は `T` になり、`printf` は `U` のままです。さきほどと同じですね。

### リンクエラーを起こす

`user.o` を渡さずにリンクしようとすると当然エラーになりますが、今はエラーメッセージをより高い解像度で理解できるようになっているはず。

```text
$ gcc main.o -o main
/usr/bin/ld: main.o: in function `main':
main.c:(.text+0x3e): undefined reference to `print_user'
collect2: error: ld returned 1 exit status
```

- `print_user` がない、というのは、指定されたファイルの中に必要なシンボルが見つからないということ
- `main.c` の `.text+0x3e` というのは機械語の位置を表していること
- リンカで、`collect2` は `ld` というプログラムを呼び出していて、実際のエラーは `ld` が出していること

などが読み取れると思います。

`ld` というと先ほど挙げた「ローダ」みたいな名前ですがそうではなく、これがリンカの本体です。`collect2` はいろいろと情報を集めて実際のリンク作業は `ld` にやらせています。なぜローダみたいな名前になっているのかというと歴史的経緯みたいです。

## ライブラリ（静的ライブラリ）

分割したファイルが 10 個、20 個と増えてくると、リンクするときに毎回すべての `.o` ファイルをコマンドラインに並べるのは大変です。そこで、複数のオブジェクトファイルをひとまとめの箱（アーカイブ）にしたものが**静的ライブラリ**（Static Library、拡張子 `.a`）です。

### 静的ライブラリを作成してリンクする

さきほどと同じソースコードを使って、静的ライブラリを作ってみます。

静的ライブラリを作るには、`ar`（アーカイブ）というコマンドを使います。`ar` はもともとは複数ファイルをひとつのアーカイブにまとめるための汎用のコマンドでしたが、今は静的ライブラリにほぼ特化して使われています。

`user.o` から静的ライブラリ `libuser.a` を作ります。

```text
$ ls
main.c  main.o  user.c  user.h  user.o
$ ar r libuser.a user.o
ar: creating libuser.a
$ ls
libuser.a  main.c  main.o  user.c  user.h  user.o
```

`r` は、アーカイブにファイルを追加するためのオプションです。アーカイブがまだ存在しないときは新規に作成してくれます。今回は対象がひとつだけですが、`user.o` の後にオブジェクトのファイル名を並べていけば複数のファイルをまとめてアーカイブできますし、あとから追加や削除も可能です。

作成されたライブラリの中身を確認してみます。`t` はアーカイブに含まれるファイルを表示するサブコマンドです。`nm` コマンドはアーカイブに対しても実行できます。

```text
$ ar t libuser.a
user.o
$ nm libuser.a

user.o:
0000000000000000 T print_user
                 U printf
```

`libuser.a` の中に `user.o` がきちんと入っていることが分かります。

では、この静的ライブラリを使ってリンクしてみましょう。

```text
$ gcc main.o -L. -luser -o main
$ ls
libuser.a  main  main.c  main.o  user.c  user.h  user.o
$ ./main
ID: 100, Name: Alice
```

できました。

`-L.` はリンク時にカレントディレクトリ（`.`）をライブラリの探し場所に追加するオプションです。指定しないと `/usr/lib` や `/usr/local/lib` などから探します。

`-luser` は `libuser.a` を探してリンクするオプションです。C 言語では、ライブラリ名から先頭の `lib` と末尾の `.a` を除いた名前（`user`）を `-l` に続けて指定する決まりになっています。

実は `-L` や `-l` を使わずとも `gcc main.o libuser.a -o main` と直接アーカイブを指定してやっても正常に実行ファイルができるのですが、開発の規模が大きくなるにつれてディレクトリとライブラリ名を指定してあとはコンパイラに探してもらう方が便利になってくるのでたいていは `-L` や `-l` で指定していると思います。

静的リンクでは、リンカがライブラリの中から必要なコードを実行ファイルの中に丸ごとコピーして取り込みます。そのため、できあがった実行ファイルは単体で完全に独立して動きます。

ライブラリを削除して試してみます。

```text
$ rm libuser.a
$ ./main
ID: 100, Name: Alice
```

動きました。

## 動的ライブラリ（共有ライブラリ）

静的ライブラリは単体で動いて便利ですが、同じライブラリを使うプログラムがたくさんあると、すべての実行ファイルに同じコードがコピーされてしまい、ディスク容量やメモリを消費します。また、ライブラリに修正があった場合、すべての実行ファイルをもう一度ビルドし直さなければなりません。

:::details 近年見直されている静的リンク
そういった問題もあるのですが、自分専用にライブラリを持っているためライブラリのバージョン不整合が起きないというメリットがあり、近年は静的リンクが見直されてきています。Go 言語でシングルバイナリと呼ばれている形式が静的リンクによる実行ファイルです。
:::

そこで広く使われているのが**動的ライブラリ**（共有ライブラリ、Linux では `.so`、Windows では `.dll`）です。

動的ライブラリでは、実行ファイルの中にライブラリのコードを埋め込みません。代わりに、「実行するときにこのライブラリを読み込んで使ってね」という目印だけを実行ファイルに記録しておきます。

### 動的ライブラリを作成する

実際に動的ライブラリを作ってみます。

```text
$ rm main
$ ls
main.c  main.o  user.c  user.h  user.o
$ gcc -fPIC -shared user.c -o libuser.so
$ ls
libuser.so  main.c  main.o  user.c  user.h  user.o
```

`-fPIC` は位置独立コード（Position Independent Code）を作るオプションです。共有ライブラリは複数のプログラムからメモリ上の色々な場所に配置されるため、「メモリのどこに置かれても動く機械語」にしておく必要があります。さきほど call 命令で呼び出し先を相対的に指定していることを見ましたが、これも位置独立にするための手段の一部です。

`-shared` は共有ライブラリとして出力するオプションです。

では、先ほど作った `main.o` をこの `libuser.so` とリンクしてみましょう。

```text
$ gcc main.o -L. -luser -o main
$ ls
libuser.so  main  main.c  main.o  user.c  user.h  user.o
```

コマンドラインは静的リンクのときと同じです。`.a` でも `.so` でも探してくれます。両方見つかったら `.so` の方を使うようになっています。

動かしてみましょう。

```text
$ ./main
./main: error while loading shared libraries: libuser.so: cannot open shared object file: No such file or directory
```

「そんなライブラリファイルはないよ」というエラーになります。想定内です。

### 動的ライブラリ情報を調べる

`readelf` の `-d` オプションで、実行ファイルに記録された動的ライブラリの情報を見ることができます。いろいろな情報が含まれていますので、`grep` で必要とする行だけを表示します。

```text
$ readelf -d main | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libuser.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

`(NEEDED)` という表示は `DT_NEEDED` タグのついた情報ですよ、ということを示します。DT は Dynamic Tag から来ています。ここでは省略されていますが、`DT_NEEDED` という形で言及されることの方が多いので `DT_NEEDED` で覚えてください。

`DT_NEEDED` タグの項目には実行時に必要となるライブラリ名が記録されます。ファイル名だけが書いてあり、パスの情報は含まれていないことに注意してください。`DT_NEEDED` タグに記録される `libuser.so` や `libc.so.6` といった動的ライブラリの名前を SONAME（Shared Object Name）と言います。

`ldd` コマンドでは、記録された動的ライブラリの名前をもとに、実際に動的ライブラリを探した結果を表示することができます。

```text
$ ldd main
	linux-vdso.so.1 (0x000077681bb50000)
	libuser.so => not found
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x000077681b800000)
	/lib64/ld-linux-x86-64.so.2 (0x000077681bb52000)
```

`libuser.so => not found`（見つからない）と表示されています。

プログラムを実行するとき、ローダは普段のライブラリ置き場（`/usr/lib` や `/usr/local/lib` など）を探しに行きます。セキュリティ上の理由から、カレントディレクトリは探してくれないため、見つけられずにエラーになったというわけです。

### LD_LIBRARY_PATH を指定して動かす

動的ライブラリを探す場所を指定するには、環境変数 `LD_LIBRARY_PATH` を使います。

コマンドラインで `<環境変数>=<値> <実行ファイル>` と書くと、環境変数に値を設定した状態で実行ファイルを実行してくれます。

```text
$ LD_LIBRARY_PATH=. ./main
ID: 100, Name: Alice
```

動くようになりました。

`LD_LIBRARY_PATH=.` と設定したおかげで、ローダがカレントディレクトリから `libuser.so` を見つけ出し、メモリ上に読み込んでシンボルを繋いでくれたというわけです。これが**動的リンク（実行時ロード）**です。

### 動的ライブラリのパスを実行ファイルに埋め込む

動的ライブラリのパスを指定するには、 `LD_LIBRARY_PATH` を使う方法だけでなく、リンクするときに実行ファイル自身の中に「ライブラリの探し場所」を書き込んでおく方法があります。

これには、`-Wl,-rpath` というオプションを使います。

```text
$ gcc main.o -L. -luser -Wl,-rpath,'$ORIGIN' -o main
```

意味は次の通りです。

- `-Wl,`: `gcc` からリンカ（`ld`）へオプションをそのまま横流しする指示です。`gcc` 自体では指定しきれない細かい指示を出すときに使います。
- `-rpath`: 実行ファイルの中に「実行時ライブラリ探索パス」を書き込むリンカのオプションです。
- `'$ORIGIN'`:「実行ファイルが置いてあるディレクトリ」を表す特別な変数です。シェル（bash）に勝手に展開されないよう、シングルクォート `' '` で囲んでいます。たいていは具体的なパスではなく `$ORIGIN` を指定します。

リンクした実行ファイルの中身を `readelf -d` で確認してみましょう。書き込んだライブラリのパスは `RUNPATH` という項目に記録されています。

```text
$ readelf -d main | grep -E '(NEEDED|RUNPATH)'
 0x0000000000000001 (NEEDED)             Shared library: [libuser.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN]
```

`$ORIGIN` が記録されました。`RUNPATH` に `$ORIGIN` が記録されていると、ローダは実行ファイルのあるディレクトリから動的ライブラリを探してくれます。

では、今度は `LD_LIBRARY_PATH` を付けずに、普通に実行してみます。

```text
$ ./main
ID: 100, Name: Alice
```

`LD_LIBRARY_PATH` を指定しなくても、同じディレクトリにある `libuser.so` を自動で見つけて起動できるようになりました。

### 動的ライブラリのパスを指定してリンクする

先ほど `libuser.so` をリンクするとき `-L. -luser` と指定しましたが、実は普通にファイル名を書くこともできます。単に `libuser.so` と指定した場合はさきほどと同じものができます。

```text
$ gcc main.o libuser.so -o main
$ LD_LIBRARY_PATH=. ./main
ID: 100, Name: Alice
$ readelf -d main | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libuser.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

パスを含めて指定した場合は（絶対パスでも相対パスでも）そのパスが `DT_NEEDED` に記録され、ローダは指定されたとおりに動的ライブラリを探しに行きます。こうしても `LD_LIBRARY_PATH` の指定は不要になりますが、必ずそのパスに動的ライブラリを置いておく必要があるため通常はこのような指定は行われません。

```text
$ gcc main.o ./libuser.so -o main
$ readelf -d main | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [./libuser.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
$ ./main
ID: 100, Name: Alice
```

普通は `libuser.so` と `./libuser.so` は同じ意味になりますが、リンクにおいては違う意味になりますのでうっかりこういった書き方をしないようにしてください。`-L. -luser` の書き方にしておくのが安全でしょう。ディレクトリを分けて指定することができるので、ビルド資材の管理も楽になります。

### 動的ライブラリに SONAME を埋め込む

先ほど「`DT_NEEDED` に記録される動的ライブラリの名前を SONAME という」と説明しましたが、`libuser.so` にはこれまで明示的に SONAME を設定していませんでした。

`readelf` で `libuser.so` 自身の中身を確認してみましょう。

```text
$ readelf -d libuser.so | grep SONAME
$
```

何も出力されません。SONAME が設定されていなかったため、リンカはリンク時に指定されたファイル名（`libuser.so`）をそのまま `DT_NEEDED` に書き込んでいたのです。

では、ライブラリに正式な SONAME を埋め込んでみましょう。

リンカオプション `-Wl,-soname,<名前>` を使うと、ライブラリの中に SONAME を埋め込むことができます。Linux の慣習に沿って、実体ファイルをバージョン付きの `libuser.so.1.0.0` とし、メジャーバージョンを表す `libuser.so.1` を SONAME として指定してビルドしてみます。

```text
$ gcc -fPIC -shared -Wl,-soname,libuser.so.1 user.c -o libuser.so.1.0.0
```

`readelf` で確認します。

```text
$ readelf -d libuser.so.1.0.0 | grep SONAME
 0x000000000000000e (SONAME)             Library soname: [libuser.so.1]
```

ライブラリの中に `Library soname: [libuser.so.1]` という公式名が埋め込まれました。

### SONAME を埋め込んだライブラリをリンクする

`-luser` でライブラリを指定すると、コンパイラは `libuser.so` という名前のファイルを探しますが、今はその名前ではライブラリが存在していないため、実体へのシンボリックリンクを作成します。

```text
$ rm libuser.so
$ ln -s libuser.so.1.0.0 libuser.so
$ ls -l libuser*
lrwxrwxrwx 1 ... libuser.so -> libuser.so.1.0.0
-rwxr-xr-x 1 ... libuser.so.1.0.0
```

この状態で、`main.o` を `-luser` でリンクしてみます。

```text
$ gcc main.o -L. -luser -o main
```

できあがった `main` の `DT_NEEDED` を確認します。

```text
$ readelf -d main | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libuser.so.1]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

リンク時に参照される動的ライブラリの実体は `libuser.so.1.0.0` ですが、リンカはそのファイル名ではなく、`libuser.so.1.0.0` に埋め込まれた SONAME を読んで実行ファイルの `DT_NEEDED` に記録しています。

このまま実行してみましょう。カレントディレクトリには `libuser.so` と `libuser.so.1.0.0` があります。

```text
$ LD_LIBRARY_PATH=. ./main
./main: error while loading shared libraries: libuser.so.1: cannot open shared object file: No such file or directory
```

`libuser.so` が目の前にあるのに、「`libuser.so.1` が見つからない」というエラーになりました。ローダはリンク時のファイル名ではなく、`DT_NEEDED` に記録された SONAME（`libuser.so.1`）を探していることが分かります。

実行時用のシンボリックリンク `libuser.so.1` を作成すると無事起動できます。

```text
$ ln -s libuser.so.1.0.0 libuser.so.1
$ ls -l libuser*
lrwxrwxrwx 1 ... libuser.so -> libuser.so.1.0.0
lrwxrwxrwx 1 ... libuser.so.1 -> libuser.so.1.0.0
-rwxr-xr-x 1 ... libuser.so.1.0.0
$ LD_LIBRARY_PATH=. ./main
ID: 100, Name: Alice
```

面倒なように見えますが、Linux では共有ライブラリを次のように管理するのがお作法になっています。

1. `libuser.so`（リンカ用）: 開発者が `-luser` でビルドするときに使われるシンボリックリンク
2. `libuser.so.1`（実行時用 = SONAME）: 実行時にローダが探すシンボリックリンク（メジャーバージョン）
3. `libuser.so.1.0.0`（実体ファイル）: 実際の機械語が入っているファイル

こうしておくと、開発時はライブラリのバージョンによらず `-luser` でコンパイルできますし、バグ修正などのマイナーアップデートで `libuser.so.1.0.1` を作った場合などは、`libuser.so.1` のリンク先を新しいファイルに向けるだけで、既存のプログラムを一切再コンパイルすることなく安全にライブラリを更新できます。

## glibc のバージョン

ここまでさらっとスルーしてきましたが、`printf` などの C 言語の標準機能は glibc（GNU C Library）と呼ばれる動的ライブラリとして提供されています。これにより、私たちが作る C 言語の実行プログラム全部に標準機能をつけておく必要がなくなっています。

ところで `glibc` には 3 種類のバージョンがあります。

ひとつめは SONAME に書かれたバージョン[^no-established-name]です。ABI バージョンなどと呼ばれるものです。glibc の実体は `libc.so.6` という名前の共有ライブラリなんですが、この `6` がそれです。こちらは根本的な非互換があるときに数字が増えることになっています。このバージョンはなんと 1997 年からずっと 6 のままです。こちらはそれほど意識しなくても問題ないでしょう。

[^no-established-name]: 特に区別したいときは SONAME バージョン・ABI バージョン・メジャーバージョンなどと呼ばれるようですが、定まった名前はないように見えます。

もうひとつは定期的に行われる修正のたびに上がる普通の意味でのバージョンです。私の環境で使われている glibc のバージョンは 2.35 でした。

```text
$ ldd --version
ldd (Ubuntu GLIBC 2.35-0ubuntu3.15) 2.35
...
```

SONAME のバージョンとソフトウェアのバージョン（メジャーバージョン）は一致させるのが普通ですが glibc の場合は歴史的経緯で数字が乖離してしまっていて少々混乱します。まずはこの 2 つのバージョンがあるんだなということだけ覚えておきます。

バージョンアップすれば当然中身も変わりますが、ビルド時に glibc 2.35 と動的リンクされた実行ファイルは実行環境でも glibc 2.35 とセットで使わないと動かないかというとそうではありません。このあたりについては 3 つめのバージョンと合わせて後で説明します。

### glibcのバージョンミスマッチを起こす

> glibc 2.35 と動的リンクされた実行ファイルは実行環境でも glibc 2.35 とセットで使わないと動かないかというとそうではありません。

そうではないのですが、バージョンが合わなくてエラーになることも（特にこの数年では）あります。

Docker を使って、手元の環境（Ubuntu 22.04）で作った実行ファイルを、少し古い OS（Ubuntu 20.04）のコンテナの中で動かして、実際にエラーを起こしてみましょう。

:::message
この練習は Docker が必要だったり、Linux のディストリビューションによってコマンドが違ってきますので、うまくいかなければ読むだけでも大丈夫です。この後の練習には影響ありません。`docker` コマンドの詳細も省略します。
:::

`main` のみを持っていけばいいように、`user.o` を直接リンクして `main` を作り直します。

```text
$ gcc main.o user.o -o main
$ ./main
ID: 100, Name: Alice
```

まずは Docker 上でもこの `main` が普通に動くことを確認します。現在使っているのと同じ ubuntu:22.04 のコンテナイメージを使って動かします。

```text
$ cat /etc/os-release 
...
NAME="Ubuntu"
VERSION_ID="22.04"
...
$ docker run --rm -v $(pwd):/app ubuntu:22.04 /app/main
ID: 100, Name: Alice
```

動きました。

では本番です。ubuntu:20.04 の環境で動かします。

```text
$ docker run --rm -v $(pwd):/app ubuntu:20.04 /app/main
/app/main: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.34' not found (required by /app/main)
```

`GLIBC_2.34` がないよというエラーになりました。

```text
$ docker run --rm -v $(pwd):/app ubuntu:20.04 ldd --version
ldd (Ubuntu GLIBC 2.31-0ubuntu9.17) 2.31
...
```

確かに glibc のバージョンは 2.31 と古いのですが 2.34 とはいったい？

### シンボルバージョニング

普通の動的ライブラリのしくみでは、SONAME と一致するファイル名が見つかる限りバージョンチェックされてエラーになることはありません[^does-not-mean-it-works]。動的ライブラリのロード自体にはそのような機能はないのです。

[^does-not-mean-it-works]: エラーにならないからと言って、ちゃんと動くと言っているわけではありません。むしろ誤動作したりクラッシュしたりする可能性があります。

今回のケースではちゃんと glibc (`libc.so.6`) 自体は見つかっています。

```text
$ docker run --rm -v $(pwd):/app ubuntu:20.04 ldd /app/main
/app/main: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.34' not found (required by /app/main)
        linux-vdso.so.1 (0x00007a70ad7d6000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007a70ad5d5000)
        /lib64/ld-linux-x86-64.so.2 (0x00007a70ad7d8000)
```

ではなぜ今回エラーになったのでしょうか。ここで「3 つめのバージョン」であるシンボルバージョンが登場します。

`nm` などでシンボルを確認したとき、`printf` は `printf@GLIBC_2.2.5` と出力されていました。この `@GLIBC_2.2.5` がシンボルバージョンです[^from-ancient-times]。ライブラリ全体のバージョンではなく、シンボルごとにバージョンがついているということです。

[^from-ancient-times]: `2.2.5` は 64bit の Linux で glibc が使われるようになった最初のバージョンだそうです。それ以来ずっと互換性が保たれているということですね！

glibc は長年にわたって改善が続けられており、関数の仕様や内部実装が新しくなることがあります。古いプログラムが動かなくなるのを防ぐため、glibc の中には過去のバージョンの関数と新しいバージョンの関数が同居しています。古い glibc とリンクされた実行ファイルから呼び出されたら古い関数を実行する、ということですね。これらを区別するためにシンボルごとにバージョンがつけられているのです。これが、SONAME のバージョンや glibc 自体のバージョンとシンボルバージョンとの決定的な違いです。

Ubuntu 20.04 の環境で実行したときのエラーから、どれかのシンボルが `GLIBC_2.34` に対応した関数を呼ぼうとしているのだと予想できます。調べてみましょう。

```text
$ readelf -sW main | grep 'GLIBC_2.34'
     1: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND __libc_start_main@GLIBC_2.34 (2)
    19: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND __libc_start_main@GLIBC_2.34
```

`__libc_start_main` という関数が `GLIBC_2.34` を要求しているようです。`__libc_start_main` といっても知らない子ですが、`main()` 関数の実行が始まる前に呼び出されてプログラム実行の準備をしてくれる関数です。通常のプログラムから呼び出すことはありません。

まず、手元の環境（Ubuntu 22.04）の glibc に `__libc_start_main@GLIBC_2.34` が含まれているか見てみましょう。

```text
$ readelf -sW /lib/x86_64-linux-gnu/libc.so.6 | grep __libc_start_main
   674: 0000000000029dc0   328 FUNC    GLOBAL DEFAULT   15 __libc_start_main@@GLIBC_2.34
   678: 0000000000029dc0   328 FUNC    GLOBAL DEFAULT   15 __libc_start_main@GLIBC_2.2.5
```

`__libc_start_main@@GLIBC_2.34` ともうひとつ、`__libc_start_main@GLIBC_2.2.5` というシンボルが含まれています。glibc 2.33 まではこちらの古い関数が呼び出されていたということですね。なお、出力で `@@` と `@` が 2 つ付いている方は、新しくリンクするときに標準で使われるデフォルトのバージョンを表します。

Ubuntu 20.04 の方の glibc 2.31 ではどうでしょうか。

```text
$ docker run --rm ubuntu:20.04 bash -c '
    apt-get update -qq && apt-get install -y -qq binutils > /dev/null
    readelf -sW /lib/x86_64-linux-gnu/libc.so.6 | grep __libc_start_main
'
debconf: delaying package configuration, since apt-utils is not installed
  2238: 0000000000023f90   483 FUNC    GLOBAL DEFAULT   15 __libc_start_main@@GLIBC_2.2.5
```

`__libc_start_main@@GLIBC_2.2.5` しかありません。そのため、`__libc_start_main@GLIBC_2.34` を探そうとして見つからない、というエラーが出たというわけです。

謎解き終了。

古い glibc しか入ってない環境で動かす実行ファイルを作るときは古い glibc でリンクしておかないとエラーが出てしまう、ということですね。逆に、古い glibc でリンクした実行ファイルを新しい glibc が入った環境で動かすときは、新しい glibc に古いシンボルが残されているので問題なく動くというわけです。

## クロスコンパイル

手元の PC で開発して、別のコンピュータ（Raspberry Pi のような小型機器や、別 OS のサーバー）向けに実行ファイルを作ることをクロスコンパイル（Cross Compile）と呼びます。

クロスコンパイルが必要になるのには、大きく分けて 2 つの理由があります。

- CPU の違い（命令セットの違い）
- OS の違い（動的ライブラリやシステムコールの違い）

PC で広く使われている CPU（x86_64）と、スマートフォンや Raspberry Pi で使われている CPU（ARM/AArch64）では、CPU が理解できる機械語（命令セット）そのものが違います。対象となる機器で動かすには、当然その CPU に合った機械語を出力する必要があります。

実行ファイルがどの CPU 向けに作られているかは、ELF ヘッダに記録されていて、もし、異なる CPU 向けのバイナリを無理に実行しようとしても、ローダがヘッダを確認してすぐに拒否してくれます。

```text
$ readelf -h main | grep 'Machine:'
  Machine:                           Advanced Micro Devices X86-64
```

では、CPU が同じなら別の OS のバイナリも動くのかというと、実はそう簡単にはいきません。

Linux と FreeBSD はどちらも UNIX の流れを引く OS ですが、基本的なしくみが異なりますし、同じ Linux 同士であってもディストリビューションが違えば標準ライブラリ（glibc）のバージョンや設定が異なります。そのため、ターゲット OS 向けに正しくビルドするためには、開発用 PC にあるヘッダファイルやライブラリではなく、ターゲットとなる OS から持ってきたヘッダファイルやライブラリを使ってコンパイル・リンクする必要があります。

このターゲット環境のディレクトリ一式（`/usr/include` や `/usr/lib` など）を丸ごとまとめたものを sysroot（システムルート）と呼びます。

gcc には `--sysroot` というオプションがあり、次のようにターゲット OS の環境を指定してビルドすることができます。

```text
$ gcc --sysroot=/path/to/target_rootfs main.c -o main
```

sysroot を作ってクロスコンパイルを実際にやってみるのも面白そうなのですが、大がかりな作業になりそうなのでここはお話だけにしておきます。

と説明しておいてなんなんですが、今はコンテナという便利なものがあるので、コンテナにして動かせる環境であればコンテナ内でビルドする方が簡単です。それができないときの手段ですね。

## 誤った動的ライブラリとのリンク

では、もし手元の PC にあるヘッダやライブラリを使ってビルドし、実行ファイルだけターゲット OS に持っていったらどうなるでしょうか？

同じ CPU（x86_64）で、同じ名前の関数を呼んでいるだけなら、そのまま動いてしまうかも？と思うかもしれません。実際、「たまたま」動いてしまうことはあります。これがこの問題の最も恐ろしく危険な落とし穴です。

### ライブラリ不整合による誤動作を体験する

共有ライブラリの不一致で誤動作する例を見てみましょう。

さきほど `user.o` を直接リンクして `main` を作ってしまったので、もう一度 `libuser.so` を作り、`main.c` とリンクして実行ファイルを作ります。

```text
$ rm libuser*
$ gcc -fPIC -shared user.c -o libuser.so
$ gcc main.c -L. -luser -o main
$ LD_LIBRARY_PATH=. ./main
ID: 100, Name: Alice
```

ここで、`user.h` を修正します。

```c:user.h
typedef struct {
    int age;        /* 追加 */
    int id;
    char name[32];
} User;

void print_user(User *u);
```

`User` 構造体に `int age;` の行を追加しただけです。関数の宣言は変更していません。

ここで動的ライブラリだけ作り直し、実行ファイル本体と共有ライブラリが整合していない状態にします。

```text
$ gcc -fPIC -shared user.c -o libuser.so
```

エラーも警告も出ずにコンパイル・リンクが成功し、新しい `libuser.so` ができました。

この状態で `main` を実行します。これは、古いヘッダファイル・動的ライブラリでビルドした実行ファイルを、新しい動的ライブラリのある環境で動かした状況と同じです。

```text
$ LD_LIBRARY_PATH=. ./main
ID: 1667853377, Name: e
```

エラーで止まることもなく実行できましたが、出力が壊れてしまいました。

なぜこのような奇妙な結果になったのでしょうか？

`main` は `User` がこのような構造体だと思っています。`int` は 4 バイト、`char` は 1 バイトで表現されるので、`u` の 0 バイト目のアドレスから 4 バイトのメモリに `id` が、4 バイト目から 32 バイト分のメモリに `name` が配置されます。

```c
typedef struct {
    int id;         /* 0バイト目から4バイト分 */
    char name[32];  /* 4バイト目から32バイト分 */
} User;
```

一方、新しくできた `libuser.so` は 0 バイト目から 4 バイトのメモリに `age` が、4 バイト目から 4 バイトのメモリに `id` が、8 バイト目から 32 バイト分のメモリに `name` があると思っています。

```c
typedef struct {
    int age;        /* 0バイト目から (4バイト) */
    int id;         /* 4バイト目から (4バイト) */
    char name[32];  /* 8バイト目から (32バイト) */
} User;
```

並べて書くとこういうことです。

| 項目 | +0 〜 +3 | +4 | +5 | +6 | +7 | +8 | +9 | +10以降 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **`main` が思っている配置** | `id` | `name` | → | → | → | → | → | ... |
| **`main` が書いたデータ** | `100` | `A` | `l` | `i` | `c` | `e` | `\0` | ... |
| **`so` が思っている配置** | `age` | `id` | → | → | → | `name` | → | ... |

そのため、`libuser.so` は `u` のメンバーがこのような値だと思って `printf` を実行し、上のような結果になったというわけです。

* `age`: 100
* `id`:  `A` `l` `i` `c` の 4 バイトを `int` と解釈した値(=1667853377)
* `name`: `e` で始まって `\0` で終わる 1 文字の文字列

このように、構造体や関数呼び出しがメモリ上にどう表現されているか（や、本記事では触れませんがレジスタの使い方も）を ABI (Application Binary Interface) と言います。API と似ていますが、API はソースコードレベルの話で、ABI はもっと物理に寄った概念になります。C 言語で正しくライブラリを利用するには API だけでなく ABI まで一致する必要があります。

`objdump` で `libuser.so` の中身を見ると実際ずれたところを読んでいることを確認できます。

```text
$ objdump -d libuser.so | grep -A 15 "<print_user>:"
0000000000001119 <print_user>:
    ...
    112d:	48 8d 50 08          	lea    0x8(%rax),%rdx  # name を8バイト目から読んでいる
    1131:	48 8b 45 f8          	mov    -0x8(%rbp),%rax
    1135:	8b 40 04             	mov    0x4(%rax),%eax  # id を4バイト目から読んでいる
    ...
```

`%rax` に構造体 `u` の先頭アドレスが入っており、`0x4(%rax)` や `0x8(%rax)` が先頭から 4 バイト目・8 バイト目を表しています。機械語になじみのないひとはそういうものだと思って読み進めていただいて差し支えありません。

今回はこのように、間違った値が表示される程度の影響で済みましたが、もし `age` がポインタだったらどうでしょう？想定外のメモリにアクセスしようとしておそらくは Segmentation Fault になるでしょう。

今回は手元の環境で無理やり不一致を発生させましたが、実行ファイルだけをターゲットの環境にインストールし、共有ライブラリはそこにもともとあったものを使おうとするとこういった不一致が発生しかねません。そのため、クロスコンパイルではターゲット環境と完全に一致したヘッダとライブラリ（sysroot）を使ってビルドする必要があるのです。

タチの悪いのは、リンカはシンボル名しか見ていなくて構造体の中身は気にせず、ローダは CPU さえ合っていればメモリの配置までは気にしないためエラーは検出されず、実行時、しかも実際に不具合が発生するまでは普通に動いてしまうことです。いつもは動いているのに、何かの条件で該当するコードに入ったときだけ誤動作が発生するといったことになり、検出が遅れる可能性があります。
