4.1 のように、多くの箇所を修正するとどこかに修正漏れがないか心配になりますね。コンピュータに確認を手伝ってもらいましょう。型ヒントを導入します。

型ヒントとはたとえば以下の `: Ident` や `-> Value` のようなものです。

```py
    def define(self, ident: Ident, val: Value) -> Value:
```

ここでは、引数の `ident` は `Ident` 型で、 `val` は `Value` 型、そして `define()` は `Value` 型の値を返す、ということを示しています。`Value` 型については後程説明しますが、「値」の型として定義します。ほかにも `Token` 型、 `Expr` 型などを定義して使っていきます。

この型ヒントにより、`define()` のひとつめの引数に `Ident` 型のオブジェクトではなく `str` を渡そうとするとエディタが「そこは `str` じゃないよ `Ident` だよ」と教えてくれるようになります。以下は `param`（`Ident` 型）を渡すべきところで `param.name`（`str` 型）を渡してしまったときの表示です。

![](/images/learning-by-growing-language/020402.type-warning.png)

このように、型ヒントは間違いの発見に役立ちますが、それだけではなくプログラムを読む人にも役立ちます。それは、`define()` というのは `Ident` 型と `Value` 型を取って `Value` 型の値を返すメソッドなんだな、ということがひと目でわかるからです。

たとえば以下の例では `eval()` は `Expr`（つまり「式」）と `Environment` を取って `Value`（つまり「値」）を返すメソッドなんだなということがわかります。これはもうほとんど `eval()` が行うこと、つまり「式」を計算して「値」を返すこと、を説明してしまっています。

```py
    def eval(self, expr: Expr, env: Environment) -> Value:
```

ここで押さえておかないといけないのは、Python 自体は型ヒントは必要としていない、それどころか型ヒントが合っていなくても普通に実行してしまうということです。型ヒントをチェックするツールは Python とは別に提供されていて、エディタではそれらを使ってソースコードをチェックします。

そのため、型ヒントはつけてもつけなくてもよく、どれだけつければ十分かというはっきりした基準はありません。どれだけの厳密さを求めるか、そのためにどれだけ手間をかけるかは型ヒントをつける目的しだいです。

現に、さっきから `ident: Ident` とか `expr: Expr` とか、そんなの書かなくてもわかりそうな型ヒントをつけていますが、これは第 1 部で型ヒントがなくてもある程度型を想像することができるように変数名を決めていたからです。`def eval(self, expr, env):` と書いてあれば `expr` が「式」で `env` が「環境」であることは想像がつくでしょう。`eval()` が「値」を返すことは読み取れませんが、コメントをつけるという手もあります[^comment-sync]。

[^comment-sync]: ソースコードを修正したとき、忘れずにコメントも修正してソースコードとコメントが乖離しないようにすることはプログラムのメンテナンスの中でも最も難しいことのひとつと言われます。忘れずに更新しましょうね、というだけなんですがこれがなかなかできない。

ひとつの明白な基準としては「全部つける」というものがありますが、ちょっと手間がかかりますし、肝心のロジックが型ヒントに埋もれてしまうということも発生しかねません。Toil のソースコードでは、パブリックなメソッド（メソッド名がアンダースコアで始まらないもの）と、空のコレクション（配列や辞書など、複数の値をまとめて保持するもの）とに型ヒントをつける方針にします。

パブリックなメソッドは、クラスのインタフェースとなる部分で、クラスを使う側から見るとパブリックなメソッドの使い方さえわかればクラスが使えますので、たとえば `define()` のひとつ目の引数には `Ident` 型を渡さないといけないんだな、だとか `eval()` すると `Value` を返してくれるんだな、ということがわかっていれば十分なわけです。

空のコレクションに型ヒントをつけるのはちょっと意味合いが違っていて、 `a = []` と書いてあってもこの配列に何が入るかまったく手掛かりがありませんが、`a: list[int] = []` と書いてあれば `int` の配列なんだな、ということがわかります。まさしく「ヒント」を提供しましょう、という感じです。 

また、タプル型については要素の型までは指定せず、単に `tuple` と表すだけにしました。これだとタプルの中身の型は気にしないことになります。たとえば `(Ident("define"), [Ident("a"), 2])` の型は細かく書けば `tuple[Ident, list[Ident | Expr]]` と書けますが、これをいろんな種類の AST すべてについて書く、というところまではやりませんでした。

Python の型ヒントは「漸進的型付け」（gradual typing）と言って、つけなくてもいいしつけるにしてもつけたいところにつけたい詳細さでつければよいので、もっと細かくチェックしてほしいなあ、と思ったら追加していけばよいようになっています。Toil ではそこそこの手間でそこそこの効果を狙うやりかたです。そのため、どんなミスも見つけてくれるというわけには残念ながら行きません。このあたりは好み（かっこよくいえば思想）にもよるところなので自分の思う最適ポイントを探ってください。

さて（長い）前置きはこれくらいにしてコードの修正点を見ていきます。あちこち修正はしますが `Ident` の導入みたいなことはないのでご安心ください。

ファイルの先頭から見ていきます。今回も `-` の行はなしで。

```diff py
+from __future__ import annotations

 class Ident:
     __match_args__ = ("name",)
 
+    def __init__(self, name: str) -> None: self.name = name
     def __hash__(self): return hash(self.name)
     ...
```

`from __future__ import annotations` [^future-doc] は、まだ Python 標準とはなっていない `annotations` という機能を有効にしますよ、という意味です。標準になっていないとは言っても、ベータ版で不具合があるかもというわけではなくきちんと動くことは保証されていますので心配無用です。`annotations` は標準になっていないとはいえわりと昔に取り入れられた機能で、そういう意味でも安心です。`annotations` がどういう機能かについては `Environment` のところで説明します。

[^future-doc]: `from __future__ import` という形は通常の `from-import` とは別物として扱われ、「future 文」と呼ばれます。詳細に関しては https://docs.python.org/ja/3/reference/simple_stmts.html#future をご覧ください。


パブリックなメソッドとは言いませんが、`__init__()` は大事なインタフェースなので型ヒントを付けます。`__init__()` の戻り値は `None` というお約束です。何か返そうとすると怒られます。

`name` はパブリックな属性ということにしていますが、`name` をもらって `Ident` オブジェクトを作ったあとは基本的には `Ident` 型のまま使い、`.name` は使わない方針でいきます。

次は大事なところです。いちいち書くと面倒な型をあらかじめ定義しておきます。`type` で型に名前を付けることができます。`|` はご想像通り「または」を表します。

```diff py
 ...
 def is_ident(s): return is_ident_first(s[0])
 
+from typing import Callable
+
+type Token = None | bool | int | Ident
+type Expr = None | bool | int | Ident | tuple
+type Value = None | bool | int | Callable | tuple
+type Instruction = tuple

 class Scanner:
     ...
```

`Callable` は「呼び出せるもの」の型で、Toil では組み込み関数の `lambda args: ...` がこれにあたります。素の Python では定義されていないので、`typing` モジュールからインポートしてやる必要があります。

`Token` はトークンを表す型で、`None` または `bool` または `int` または `Ident` と定義します。`Scanner` クラスを見るとこれらの型だけをトークンとして使っているはずです。`|` は「または」で、いくつかの型を取る可能性があるときに使います。

`Expr` は「式」を表す型で、`tuple` 型も含みます。`(Ident("define"), ...)` のようなものですね。

`Value` は「値」を表す型で、`Callable` が含まれます。たとえば `add` の値は `lambda args: args[0] + args[1]` ですので。

`Instruction` は仮想マシンの命令を表す型です。ここも `tuple` で済ませています。

次は `Scanner` クラスです。

```diff py
 class Scanner:
+    def __init__(self, src: str) -> None:
         self._src = src
         ...
+        self._tokens: list[Token] = []
 
-    def tokenize(self):
+    def tokenize(self) -> list[Token]:
         ...
```

`Scanner` の `__init__()` は `str` 型でソースコードをもらいます。`self._tokens: list[Token] = []` は「空のコレクションには型ヒントをつける」という決めに従って付けました。`_tokens` はトークンの配列です。

`tokenize()` は引数を取らず、`list[Token]` を返すメソッドです。

このあたりを見るだけで、`Scanner` はソースコードをもらってトークンの配列を返すクラスなんだな、ということがだいたいわかります。

`Parser` クラスです。

```diff py
 class Parser:
+    def __init__(self, tokens: list[Token]) -> None:
         self._tokens = tokens
         self._pos = 0
 
+    def parse(self) -> Expr:
         ...
```

トークンの配列をもらって AST（`Expr`）を返すクラスですね。読み方の雰囲気はわかってきましたか？

`Environment` クラスに進みます。

```diff py
 class Environment:
+    def __init__(self, parent: Environment | None = None) -> None:
         self._parent = parent
+        self._vars: dict[Ident, Value] = {}
 
+    def define(self, ident: Ident, val: Value) -> Value:
         ...
 
+    def assign(self, ident: Ident, val: Value) -> Value:
         ...
 
+    def val(self, ident: Ident) -> Value:
         ...
 
+    def bind(self, params: list[Ident], args: list[Value]) -> None:
         ...
```

`Environment | None` は `Environment` または `None` のどちらか、ということで、最上位の環境なら `None` 、そうでなければ親環境を渡します。

なお、Python がここを読んでいる時点では `Environment` 型がまだ存在していない（`class Environment:` のブロックを最後まで読んではじめて `Environment` 型が定義される）ため、以前の Python だとこの書き方ではエラーになっていました。それを防ぐのがファイルの先頭に追加した `from __future__ import annotations` です[^annotations-details]。これによって型ヒントの評価が回避され、まだ定義されてないクラス名でも型ヒントとして使えるようになります。

[^annotations-details]: `annotations` がなかったころ、または今でも `annotations` が有効でない場合は `"Environment | None"` のように文字列として書く必要がありました。文字列なので中に何が書いてあろうと Python 自身はエラーにしないというわけです。`annotations` に関する詳細は https://peps.python.org/pep-0563/ をどうぞ。本文では「回避」と書きましたが Python のドキュメントでは「遅延」と書かれます。必要になるまでは評価しない、という意味で「遅延」なのですが、Python 自身は型ヒントを必要としないので、いつまでも評価されないため「回避」としました。ただし、Python プログラム自身が型ヒントを要求することもでき、その場合は評価されます（ややこしい）。

`self._vars: dict[Ident, Value] = {}` はやはり「空のコレクションには型ヒントをつける」ルールに従ったものです。`dict[Ident, Value]` というのは、キーが `Ident` で値が `Value` な辞書、ということです。

`Environment` クラスのメソッドはどれもパブリックなのですべて型ヒントをつけています。

あとは同じようなパターンなのでわかると思います。やはり `Compiler`・`VM` クラスもここで型ヒントを付けておきます。

```diff py  
 class Evaluator:
+    def eval(self, expr: Expr, env: Environment) -> Value:
         ...
 
     ...
 
 class Compiler:
+    def __init__(self, expr: Expr) -> None:
         self._expr = expr
+        self._code: list[Instruction] = []
 
+    def compile(self) -> list[Instruction]:
         ...
 
     ...
 
 class VM:
+    def __init__(self, code: list[Instruction], env: Environment) -> None:
         ...
+        self._stack: list[Value] = []
+        self._ctrl_stack: list[tuple] = [("call", [("halt",)], 0, env)]
 
+    def execute(self) -> Value:
         ...

     ...

 class Interpreter:
+    def __init__(self) -> None:
         self._env = Environment()
         self._builtins()
 
     ...
 
+    def scan(self, src: str) -> list[Token]:
         return Scanner(src).tokenize()
 
+    def parse(self, tokens: list[Token]) -> Expr:
         return Parser(tokens).parse()
 
+    def ast(self, src: str) -> Expr:
         return self.parse(self.scan(src))
 
+    def eval(self, expr: Expr) -> Value:
         return Evaluator().eval(expr, self._env)
 
+    def walk(self, src: str) -> Value:
         return self.eval(self.ast(src))
 
+    def compile(self, ast: Expr) -> list[Instruction]:
         return Compiler(ast).compile()
 
+    def code(self, src: str) -> list[Instruction]:
         return self.compile(self.ast(src))
 
+    def execute(self, code: list[Instruction]) -> Value:
         return VM(code, self._env).execute()
 
+    def run(self, src: str) -> Value:
         return self.execute(self.code(src))
 
 ...
```

さきほども書いた通り、プログラムの実行時には型ヒントは無視されますので、文法エラーさえなければそのまま動くはずです。手元の環境では警告も出ないようになっていますが、完全なものではないのでもしかするとチェックするツールによっては警告が出るかもしれません。もし出てしまったら [読者コミュニティ](https://zenn.dev/kb84tkhr/scraps/3f5cc9140d4bf2) でご連絡ください！

## コラム：動的型付け・静的型付け・漸進的型付け

本文中に「漸進的型付け」なる用語が突然出てきました。比較的新しい考えなのでなじみのない人もいるかと思います。「漸進的型付け」に対して、古くからあるのは「静的型付け」（static typing）と「動的型付け」（dynamic typing）です。その古さはというと Fortran と Lisp というプログラミング言語の黎明期にまで遡ります。まずこれらの考え方から紹介しましょう。

静的型付けというのは、変数の型は実行前に決まっているということを指します。`int` 型の変数には `int` 型の値しか入れることができず、型の違う値を入れようとしていないか、実行前にチェックすることができます[^check-in-advance]。

[^check-in-advance]: 実際にチェックするかどうかは処理系の考え方にもよります。最も初期の C 言語ではほとんどチェックされていなかったそうです。

さて、変数はよく箱に例えられます。`a` という名前の箱があってそこに `2` という値を入れる、みたいな感じで。箱の例えは静的型付け言語にはよく合うのですが、動的型付け言語に関しては実を言うとあまりピッタリくる例えではありません。動的型付け言語については、まず値があり、変数名はその値につけられたラベルに過ぎない、と考えたほうがよりよく処理系の動きをイメージすることができます。これまで Toil の処理系を書いてこられた方には雰囲気が伝わるのではないかと思います。動的型付け言語の祖先である Lisp のような言語では「変数に値を入れる」のようには言わず、「値に名前をバインドする（bind: 結びつける・束縛する）」という言い方をします。これも変数名がラベルであるというのと共通した考え方からくるものです。

型付けの話に戻ると、動的型付けというのは、変数の型は値にバインドされた時、つまり実行された時に決まるということになります。「動的型付け言語には型がない」ように言われることもありますが、読者の方にはおわかりのようにそんなことはありません。動的型付け言語では「値」に型があるのです。

静的型付け・動的型付けのどちらがよいかについてはずっと議論されてきました。簡単に言うと静的型付けのメリットは保守性の高さ・高速・省リソース、動的型付けのメリットは手軽さ・開発速度・柔軟性であると言えます。静的型付けが安全なのは事前にチェックが行えるということでわかりやすいと思いますが高速というのはどういうことかと言えば、「この変数は `int` である」などと決め打ちして処理ができる、ということです。Python では `a + b` という式は `a` が `int` か `float` か `str` か（ほかにもあるかな？）判断してからでないと処理することができません。何度も実行する場合でももしかすると型が変わっているかもしれないので毎回チェックする必要があります。一方、静的型付け言語では実行前に `int` なら `int` と決まっているので `a + b` ならただ `int` の足し算をするだけでいいわけです。こっちの方が性能がよいのはわかりますね。省リソースであることについても同じような話です。

「静的型付け」と「動的型付け」の間では長らく勢力争いが続いてきました。もちろん利用用途にもよるのですがものすごくざっくり言うと 

* プログラミング言語の黎明期はコンピュータの性能・リソースが少なく、静的型付けが優勢。その後も C 言語や Java など静的型付け言語は常に一定の勢力をキープ。
* コンピュータの性能・リソースが向上する一方、ソフトウェアの開発速度が重視され、Ruby や Python といった動的型付け言語が注目・台頭。
* ソフトウェアが大規模になり、保守性の高さの重要度が増してきて静的型付け言語が見直されてきた。

といった感じでしょうか。そこで、動的型付け言語でももっと保守性を高めよう、という動きになるわけです。ただ、じゃあ型宣言するようにすればいいかというと、単純に導入するだけでは手軽さや柔軟性といった動的型付けの良さを消してしまいます。

そこで、変数の型宣言を必須とせず、つけたいところにつければよい、という漸進的型付けが生まれました。重要な関数・変数にだけ型を書いたり、開発初期は宣言を書かずに速度優先で進め、保守フェーズに進むにつれて宣言を追加していく、というような進め方もできるようになっています[^good-or-not]。

[^good-or-not]: それがよいやり方かどうかはなんとも言えません。

一方、静的型付け言語側も手をこまねいてみているわけではなく、あらゆる変数に型を書く煩雑さを避けるために型推論の機能を備え、推論できる範囲では型宣言を省略できる言語が増えてきています。結果、静的型付けでも動的型付けでも、ソースコードの見かけがちょっと似た感じになってきたような気がします。

動的型付け言語に後付けのツールで漸進的型付けを付加した場合、実行時には結局その型に関する情報は捨てられてしまい、最適化による性能向上にはつながらないというのがもったいない感じです。漸進的型付けを採用しているもっともメジャーな言語である Python と TypeScript が両方そういう形なのはちょっと残念ですが、同じく動的型付け言語である Lua ではそのあたりうまくやっているそうですし、JavaScript/TypeScript 周辺も新しい処理系が出てきていてこれから状況が変わっていきそうです。
