title: "5.4 UFCS"
---

Toil の辞書でキーを取り出したいときは `keys(d)` と書いていました。Python だと `d.keys()` と書きますね。これは `d` が `dict` 型のインスタンスで `keys()` というメソッドを持つのでこういう形になるわけですが、Toil ではちょっと違った考え方を取り入れます。

どういうものかというと、`f(a, b, c)` のような関数呼び出しを、最初の引数を前に出して `a.f(b, c)` とも書ける、というもので、UFCS (Uniform Function Call Syntax) と呼ばれています[^dlang-ufcs]。これにより `keys(d)` が `d.keys()` と書けるようになります。私は Python を使っていても `arr.len()` って書いてしまってから間違いに気づいていそいそと修正することが多いので Python にも UFCS がほしいです[^natural-for-japanese]。

[^dlang-ufcs]: D 言語などで取り入れられています。https://tour.dlang.org/tour/ja/gems/uniform-function-call-syntax-ufcs やさらに詳しくは https://dlang.org/book/ufcs.html をご参照ください。

[^natural-for-japanese]: 英語話者なら "len of arr" と思うのかもしれませんが日本語で考える人なら「`arr` の `len` は、と・・・」みたいに考えながら入れちゃいますよね？

構文が変わらないので今回の変更は `Evaluator` だけです。

```diff py
 class Evaluator:
     ...

     def _dot(self, target_expr, attr_name, env):
         target_val = self.eval(target_expr, env)
-        assert isinstance(target_val, dict), \
-            f"Invalid dot target @ _dot(): {target_val}"
-        return target_val[attr_name]
+        match target_val:
+            case dict() if attr_name in target_val:
+                return target_val[attr_name]
+            case _:
+                func_val = env.val(Ident(attr_name))
+                return (Ident("binding"), [func_val, target_val])
```

これまでは単に `target_val[attr_name]` を返していましたが、今回は `target_val` が `dict` でかつ `target_val` に `attr_name` が存在するときだけ `target_val[attr_name]` を返しています。この関係で、`[2, 3].a` が Undefined variable になるなど、これまでとエラーの出方が変わるところがあります。

そうでない場合 UFCS の処理を行います。この場合は `attr_name` を関数名とみて環境から値を探し、`(Ident("binding"), [func_val, target_val])` という値を返します。これが何者なのかちょっとわかりづらいかもしれませんが `func_val` が関数（実はクロージャ）で、`binding` は `func_val` と 1 つめの引数（`target_val`）をセットにしたものです。`bind` は「変数を bind（束縛）する」のように使い、変数名と値を対応付けるといった意味です。`Environment.bind()` で引数名と値を対応付けていましたね。

ここで作った `binding` は `_op()` で使います。

```diff py
     def _op(self, op_expr, args_expr, env) -> Value:
         op_val = self.eval(op_expr, env)
         args_val = [self.eval(arg, env) for arg in args_expr]
+        match op_val:
+            case (Ident("binding"), [func_val, target_val]):
+                op_val = func_val
+                args_val = [target_val] + args_val
         match op_val:
-            case f if callable(f): return f(args_val)
+            case f if isinstance(f, Callable): return f(args_val)
             case (Ident("closure"), [params, body_expr, closure_env]):
                 new_env = Environment(closure_env)
                 new_env.bind(params, args_val)
                 try:
                     return self.eval(body_expr, new_env)
                 except ReturnException as e: return e.val
             case _:
                 assert False, f"Invalid operator @ _op(): {op_val}"
```

`op_val` を見て `binding` だったら、引数の配列の先頭に `target_val` をくっつけてから `func_val` を普通に関数として評価しているだけです。`if callable(f)` を `if isinstance(f, Callable)` に変更しているのは、こうしないと型の警告が出たからで、深い意味はありません[^object-or-any]。

[^object-or-any]: `if callable(f)` だと `func_val` が `object` を返す関数と判断されて型の警告になるようです。`if isinstance(f, Callable)` だと `func_val` は `Any` を返す関数と判断され、何型でも OK になるので警告は消えますが特に何か解決したわけではありません。ちゃんとやるならもっと細かくヒントをつけていくとかひとつひとつクラスを定義するといった対応になります。

実行例です。

```py
    # Example

    print("UFCS:")

    print(toil.walk(r""" add(2, 3) """)) # -> 5
    print(toil.ast(r""" 2.add(3) """)) # -> ((dot, [2, 'add']), [3])
    print(toil.walk(r""" 2.add(3) """)) # -> 5
```

AST は 5.3 節の `util.double(3)` と同じ形ですがちゃんと足し算してくれています。`2` が辞書ではないからですね。

```py
    print(toil.walk(r""" f := 2.add; f(3) """)) # -> 5
```

実は `binding` もひとつの Toil の値なのでこういうこともできます。

```py
    print(toil.walk(r""" keys({a: 2, b: 3}) """)) # -> ['a', 'b']
    print(toil.walk(r""" {a: 2, b: 3}.keys() """)) # -> ['a', 'b']
```

`keys()` もメソッド風に書けるようになりました。メソッドではありませんが。

```py
    print(toil.walk(r""" {a: 2, keys: func do 3 end}.keys() """)) # -> 3
```

`keys` が実際にキーとして存在した場合は UFCS でなく辞書へのアクセスとして処理されます。ちょっとここはわかりづらいところで、`.` に要素アクセスと UFCS の 2 つの機能を重ねてしまった弊害と言えます[^design-perspective]。

[^design-perspective]: 言語設計的には 1 つの記号にいくつも意味を持たせるのは混乱を招きそうであまり推奨されないと思います。処理系もその分複雑になりますし予想外の挙動になる可能性もあります。D 言語では UFCS はありますが辞書の要素にドットでアクセスする機能はありません。でも面白いので Toil では両方採用しました。

```py
    print(toil.walk(r""" "a".in("abc") """)) # -> True
    print(toil.walk(r""" "d".in("abc") """)) # -> False
```

`in` も自然に読めるような形に。実はコレクション系の組み込み関数は基本的にコレクションを第 1 引数にしているのですが、`in` はこのためにコレクションを第 2 引数にしています。それは美しくない！と思ったら例えば `includes(<コレクション>, <要素>)` という関数を作って `"abc".includes("a")` と書けるようにするとか。

```py
    toil.walk(r""" def myadd(a, b) do a + b end """)
    print(toil.walk(r""" 2.myadd(3) """)) # -> 5
```

もちろんユーザ定義関数でも同様に UFCS が働きます。

UFCS でうれしい例です。

```py
    print(toil.walk(r"""
        def sieve(n) do
            s := [False, False] + [True] * (n - 2);
            i := 2; while i * i < n do
                if s[i] then
                    j := i * i; while j < n do
                        s[j] = False;
                        j = j + i
                    end
                end;
                i = i + 1
            # then map(filter(enumerate(s), last), first) end
            then s.enumerate().filter(last).map(first) end
        end;

        sieve(10)
    """)) # -> [2, 3, 5, 7]
```

何がうれしいかというと `s.enumerate().filter(last).map(first)` を「`s` を `enumerate()` して `filter()` して `map()` する」のように左から自然に読めることです。やっていることは `map(filter(enumerate(s), last), first)` と全く同じなのですが読みやすさは段違い。

このように、左側の結果を入力とし、出力が今度は右側の入力となって処理がつながっていく書き方をパイプラインと言います。はっきりパイプライン機能を持ってますというような言語では `|>` のようなパイプライン専用の演算子[^multi-arg-pipe]が採用されています。見た目は変わりますが、ドットに意味を重ねるのを避けるにはそういうアプローチも考えられます。

[^multi-arg-pipe]: Toil では右側の関数の最初の引数にだけ値を渡すことができますが、複数の引数に値を渡せるパイプライン演算子を持つ言語があります（F#）。`|>` なら最初の引数だけ、`||>` なら 2 つめまで、`|||>` なら 3 つめまで、という風に。ちょっと面白い表記です。使うかというとやや微妙な感じですが。

```py

    # toil.walk(r""" foo := 2; 3.foo() """) # -> Invalid operator
```
